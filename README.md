# Chainway — 服飾圖片特徵 × 銷售數據 交叉分析平台

把公司既有的四種資料串起來，回答設計師實際會問的問題：

> 歷年哪些**設計特徵**和暢銷／滯銷有關？（分品類看）
> 這款**為什麼**賣不好 —— 是設計問題，還是缺貨、陳列問題？
> 各品類各季**該開幾款**？現在的配置有沒有明顯浪費的一格？
> 這一季要開的款，**是不是三年前做過了**？
> 拿一張市調照片，能不能**反查**自家最像的款、貨號與價格？

---

## 怎麼開始用：雙擊 `開始.bat`

不用記指令。它會自己抓最新版程式、裝好環境，然後出一個選單：

```
  1   全部重跑，開啟商品清單（來源資料變了才需要，很慢）

  2   專櫃回填表單    （這週的新品）
  3   專櫃判斷校準    （他們當時說的，後來對了嗎）
  4   客戶意見調查    （LINE 流程、表單、題目稿）

  5   影像稽核        （為什麼有些款沒有照片）
  6   商品規劃展開圖  （各品類各季該開幾款）
  7   季別診斷報告    （各季完銷率）
  8   重複款偵測      （這款是不是做過了）

  9   開啟報表總覽    （有什麼、多新、卡在哪）

  0   結束
```

**不知道要按哪個就按 9。** 總覽頁會列出目前有哪些報表、各是幾天前產生的、
以及**現在卡在哪一步等你做**（那幾件事只有人做得到，不做的話後面全部停住）。

第一次跑之前，資料夾位置設定在 `config/settings.yaml` 的 `paths`。
改 `root` 一行就能整套換位置，也支援 `//NAS/...` 網路磁碟。

> **Windows 路徑請用正斜線 `/`。** YAML 雙引號裡的 `\` 是跳脫字元，
> `"C:\Users\..."` 會直接解析失敗。詳見 [`docs/data_contract.md`](docs/data_contract.md)。

## 這套系統吃什麼、吐什麼

| 輸入（公司既有） | 輸出 |
|---|---|
| 系統圖（去背商品照 + 貨號） | 設計重點位置、領型／袖長／衣長、顏色對色號 |
| 裁縫指示書（重點尺寸 + 線稿） | 版型甜蜜區間；指示書內嵌的圖也會抽出來補系統圖的缺口 |
| POS 歷年分季進銷存 | 逐款診斷：真滯銷 / 假滯銷 / 虛胖暢銷；商品規劃展開圖 |
| ★ 專櫃回填表單（發出去收回來） | 判斷校準：專櫃當時說的後來對了嗎 |
| ★ 客戶意見調查（LINE 發票回填） | 試穿沒買的原因 —— POS 永遠看不到的那一半 |
| ★ 市調照片、流行線條 | 線稿 + SVG + 平塗彩現 + 色票 + 機械圖 prompt |

## 選單以外的指令

選單蓋掉九成的日常。剩下這些是偶爾才用、或要接在別的步驟後面的：

```bash
python -m chainway.cli doctor                    # 環境／路徑／套件哪裡不對
python -m chainway.cli overview                  # 報表總覽（＝選單 9）

# 影像量測（要有系統圖，跑得慢）
python -m chainway.cli locate                    # 設計重點在衣服哪個位置
python -m chainway.cli silhouette                # 版型 × 銷售（要先跑 locate）
python -m chainway.cli color --scan-codes        # 量顏色並對到色號
python -m chainway.cli reclassify-images         # 重判指示書抽出來的圖是什麼

# 分析
python -m chainway.cli motif                     # 熊／格紋的位置・形式・比例
python -m chainway.cli inventory --stock-gap     # 兩個庫存數字差最多的款
python -m chainway.cli reverse-design            # 暢銷特徵、組合、佈局建議

# 市調圖
python -m chainway.cli sketch --image 街拍.jpg --auto
python -m chainway.cli search --image 市調照.jpg  # 以圖反查貨號與價格

# 回收客戶問卷
python -m chainway.cli customer-survey --import 匯出檔.csv
```

`serve`（FastAPI 網頁後台）還在，但**已經不是主要路徑**。報表改成雙擊就開的
HTML 檔 —— 伺服器要裝套件、要開起來、要記網址，關掉就沒了，而報表本來就不需要互動。

## ★ 兩份要人填的表，以及為什麼分成兩份

量化數據只能算出「賣得好不好」。要分辨下面這三種完全不同的狀況，一定要有人填：

| 診斷 | 意思 | 該做什麼 |
|---|---|---|
| **假滯銷** | 其實賣很好，但 M 號第三週就斷碼 | 追單、檢討尺寸配比 —— **設計不用改** |
| **真滯銷** | 客人反映橫開領太寬、肩線滑落 | 修版重出 —— 設計要改，而且知道改哪裡 |
| **虛胖暢銷** | 銷量靠折扣換來 | 追單前先複查毛利 |

**專櫃回填表單**（選單 2）給店員，每週的新品、上市兩週後填。
一款兩題：客人的反應是什麼、您自己怎麼看。**這兩題一定要分開**，
因為它們不一致的時候最有價值 —— 客人一直問但店員不看好，通常是缺色斷碼或
陳列位置，不是商品問題。

**客戶意見調查**（選單 4）給客人，上傳發票後在 LINE 上填。
最值錢的一題是**「有沒有試穿了但沒買的」** —— POS 只記錄賣掉的，
那件放回架上的衣服公司完全看不到，而它離成交只差一步。

兩份表的接點是貨號，價值一樣在不一致的地方：
客人一直說「沒有我的尺寸」＋ 店員說「賣得好」＝ 斷碼，
售罄率漂亮是因為賣完了，不是因為備夠了。

理由用**受控詞彙**（`config/feedback_tags.yaml`、`config/customer_survey.yaml`）
＋ 自由文字。受控詞彙可以統計、可以交叉；自由文字可以閱讀、可以佐證。兩者都要。

## ★ 市調圖轉線稿 —— 能做到什麼、不能做到什麼

```bash
python -m chainway.cli sketch --image "街拍_0312.jpg" --auto
```

輸出：重點裁切圖、線稿 PNG、**線稿 SVG（可開 Illustrator）**、平塗彩現圖、
色票 JSON、三欄對照頁、繁中規格書、英文繪圖 prompt。

| | 本機做得到 | 需要外部工具 |
|---|---|---|
| 局部截取重點 | ✅ | |
| 照片 → 線稿（XDoG，接近手繪筆觸） | ✅ | |
| 線稿 → SVG 向量 | ✅ | |
| 平塗彩現 + 色票 | ✅ | |
| 從照片量領型／袖長／衣長填進規格書 | ✅ | |
| 乾淨對稱的向量機械圖 | ❌ | 生成式繪圖 或 版師描稿 |
| 寫實質感彩現圖 | ❌ | 生成式繪圖 |

**本機演算法產出的是「照片的線條化」，適合當描圖底稿與細節參考，
不要直接當成可入 Tech Pack 的機械圖交給版師。**
需要正式機械圖時，產出的 `prompt.txt` + `spec.md` 可直接交給
Adobe Firefly / DALL·E / Midjourney，或交給版師照描。

規格書上每一項都會標明是**量出來的**還是人填的，量不到的寫「量不到」
而不是填一個看起來合理的預設值 —— 一份看起來完整、其實一半是猜的規格書，
比一份誠實留白的危險得多。

👉 **完整的「需要安裝／調用什麼」清單見 [`docs/skills_and_tools.md`](docs/skills_and_tools.md)**

## 方法上的誠實說明

這套系統算的是**相關**，不是**因果**。「立領上衣暢銷提升度 +34%」的正確讀法是
「過去做的立領上衣裡，成功比例較高」，而不是「把領子改成立領就會賣」——
兩者可能都受第三個因素影響（例如立領款剛好都用了較好的布）。

所以：

- **n < 20 的請視為假設，不是結論**
- 每一組都附 bootstrap 95% 區間，區間跨過 0 的一律標成「只能當方向」
- **一次比了幾組會一起報**。95% 區間的意思是「每 20 組會有 1 組就算完全沒效果、
  區間也剛好不跨過 0」；不講的話，一張表上五個「區間不跨 0」看起來像五個發現
- 影像量測的屬性（領型、袖長、衣長）**先驗準確率再給數字**。拿品名有寫的那些款
  當免費的驗證集，準確率過不了門檻的屬性照樣印出準確率與量錯的實例，
  但**不給**售罄率的比較 —— 標一句「僅供參考」沒有用，數字印出來就會被引用
- 資料涵蓋率放在報告第一節 —— 任何一環命中率低，後面就要打折扣看

### 一個真的從貴司資料算出來的例子

> 過去五年 19 季裡，**秋季最好的一年 39.5%，仍低於其他季別最差的一年 49.0%
> —— 五季 vs 十四季完全沒有重疊。**
> 五個秋季投入 58,412 件，賣掉 20,935 件。
>
> 最容易講得通的反駁是「秋季只是上架期短」。**推翻失敗**：上架天數與售罄率的
> 相關係數是 +0.298（n=19），方向還是「越久賣得越好」；而 2022 早春只賣 111 天，
> 售罄 68.4%，是十九季裡最高的。天數解釋不掉這件事。

（2,469 款納入分析，原始 2,854 款，快照 2026-08-12。
扣掉的是贈品 29、樣衣 295、投入 < 30 件 61 款。）
